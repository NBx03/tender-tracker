# Задание 6. Микросервис трекинга статуса тендеров

Сервис создаёт тендеры, меняет их статус и пишет каждое изменение в отдельную
таблицу истории: кто изменил, когда и почему.

## Состав

| Путь | Содержимое |
|---|---|
| `app/main.py` | Эндпоинты и коды ответов |
| `app/statuses.py` | Статусы и матрица допустимых переходов |
| `app/repository.py` | SQL-запросы |
| `app/schemas.py` | Модели запросов и ответов |
| `app/db.py` | Движок и транзакция на запрос |
| `app/config.py` | Строка подключения из окружения |
| `schema/01_schema.sql` | Таблицы, ограничения, индекс |
| `tests/` | 31 тест |

## Требования

Python 3.12, PostgreSQL 16. Poetry — основной способ установки, pip —
альтернативный.

## Запуск

```bash
createdb -U postgres tender_tracker
psql -U postgres -d tender_tracker -v ON_ERROR_STOP=1 -f schema/01_schema.sql
cp .env.example .env
poetry install
poetry run uvicorn app.main:app
```

При других параметрах подключения — поправить `DATABASE_URL` в `.env`.

Без Poetry:

```bash
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -e .
.venv/Scripts/python.exe -m uvicorn app.main:app
```

Файл схемы объявляет свою кодировку первой командой: без этого psql берёт
кодировку клиента из локали системы, и на русской локали Windows файл не
применяется.

Проверять запросы удобно через `http://127.0.0.1:8000/docs` — там же
кириллица в теле запроса не зависит от кодировки консоли.

## Тесты

```bash
poetry install --all-extras
poetry run pytest
```

Без Poetry: `pip install -e ".[dev]"`, затем `pytest`.

Тесты работают на отдельной базе — имя рабочей с суффиксом `_test`. Она
пересоздаётся перед прогоном из того же `schema/01_schema.sql`, поэтому тесты
попутно подтверждают применимость схемы. Рабочая база не затрагивается.

## Эндпоинты

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/tenders` | 201, созданный тендер в статусе `draft` |
| `PATCH` | `/tenders/{id}/status` | 200, тендер с новым статусом |
| `GET` | `/tenders/{id}/history` | 200, записи истории по возрастанию времени |

Чтение истории добавлено сверх требуемого: без него запись истории проверяется
только запросом к базе напрямую.

Пример:

```bash
curl -X POST http://127.0.0.1:8000/tenders \
  -H "Content-Type: application/json" \
  -d '{"title":"Server supply","changed_by":"ivanov","reason":"fits our profile"}'

curl -X PATCH http://127.0.0.1:8000/tenders/1/status \
  -H "Content-Type: application/json" \
  -d '{"status":"active","changed_by":"petrov","reason":"bid submitted"}'

curl http://127.0.0.1:8000/tenders/1/history
```

## Статусы

| Значение | Название |
|---|---|
| `draft` | Черновик |
| `active` | Активен |
| `won` | Выигран |
| `lost` | Проигран |

Допустимые переходы: `draft → active`, `active → won`, `active → lost`. Из
`won` и `lost` переходов нет: исход наступил.

Переход в текущий статус недопустим — изменения не произошло, значит и записи
в истории быть не должно.

## Алгоритм смены статуса

1. Прочитать тендер запросом `SELECT ... FOR UPDATE`. Строки нет — 404.
2. Проверить переход по матрице от прочитанного статуса. Недопустим — 409, в
   тексте ответа перечислены допустимые переходы из текущего статуса.
3. Обновить статус тендера.
4. Вставить запись истории: старый статус, новый статус, автор, причина.
5. Вернуть обновлённый тендер.

Все шаги выполняются в одной транзакции: она открывается зависимостью запроса,
фиксируется при обычном возврате и откатывается при любой ошибке. Состояния,
где статус изменён, а записи в истории нет, не существует.

Старый статус берётся из прочитанной строки, а не из запроса: клиент его не
сообщает и подделать не может.

## Одновременные запросы

`FOR UPDATE` держит строку до конца транзакции. Второй одновременный запрос
ждёт на этой же строке и после ожидания перечитывает её — то есть видит уже
новый статус и проверяет переход от него.

Десять одновременных попыток одного и того же перехода дают один ответ 200 и
девять 409. Без блокировки все десять прочитали бы исходный статус, и в
истории появилось бы десять «изменений» из одного состояния.

## Таблица истории

| Поле | Смысл |
|---|---|
| `tender_id` | Тендер |
| `old_status` | Предыдущий статус; пусто у записи о создании |
| `new_status` | Новый статус |
| `changed_by` | Кто изменил |
| `reason` | Почему |
| `changed_at` | Когда |

Создание тендера тоже попадает в историю — записью с пустым старым статусом.
Иначе история начинается с середины и происхождение черновика ничем не
подтверждено.

Оба статуса хранятся в одной строке, поэтому каждая запись самодостаточна и
цепочку не нужно восстанавливать чтением всей таблицы по порядку.

Автор и причина обязательны и не могут быть пустыми: ограничения стоят и в
схеме, и в моделях запросов.

## Коды ответов

| Код | Когда |
|---|---|
| 201 | Тендер создан |
| 200 | Статус изменён, история прочитана |
| 404 | Тендера с таким идентификатором нет |
| 409 | Переход недопустим, включая переход в текущий статус |
| 422 | Тело запроса не прошло проверку |

## Схема данных

Две таблицы: `tenders` и `tender_status_history`.

Схема задания 4 не переиспользуется. Её тендер требует заказчика
(`customer_id NOT NULL`), и создание тендера одним запросом к API стало бы
невозможным: сначала пришлось бы заводить компанию. Задания проверяются
независимо, поэтому у каждого своя схема.

Доступ к базе — SQLAlchemy Core без ORM-моделей: описание таблиц остаётся
только в SQL-файле и не может разойтись с кодом. Движок синхронный — на запрос
приходится два-три обращения к базе, асинхронность здесь ничего не ускоряет.

## Принятые решения

- «Кто изменил» передаётся в теле запроса. Аутентификации нет; в рабочем
  сервисе это значение брали бы из токена.
- Повторная установка того же статуса отклоняется с 409, а не принимается как
  успешная без изменений: тихий 200 создал бы расхождение между ответом и
  историей.
- Отсутствие тендера при чтении истории — 404, а не пустой список: запись о
  создании есть у каждого тендера, поэтому пустой ответ означал бы не
  «изменений нет», а «тендера нет».

## Границы решения

- Чтение истории тоже открывает транзакцию записи; фиксация в конце пустая.
  Отдельной зависимости только для чтения нет.
- Нет пагинации истории, аутентификации, миграций и мягкого удаления тендеров.

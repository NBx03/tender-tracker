# Задание 4. Схема БД «Тендерная площадка»

Схема для системы мониторинга госзакупок от лица участника закупок: компания
отслеживает тендеры, подаёт ставки по лотам, ведёт исход участия и назначает
исполнителей на выигранные лоты.

## Состав

| Файл | Содержимое |
|---|---|
| `01_schema.sql` | Тип статуса, шесть таблиц, первичные и внешние ключи, ограничения, индексы, комментарии к таблицам |
| `02_seed.sql` | Демонстрационные данные |
| `queries/01_top_companies_last_month.sql` | Топ-3 компании по сумме выигранных тендеров за прошлый месяц |
| `queries/02_participation_funnel.sql` | Воронка участия своей компании по месяцам |

## Запуск

```bash
createdb -U postgres tender_registry
psql -U postgres -d tender_registry -v ON_ERROR_STOP=1 -f 01_schema.sql
psql -U postgres -d tender_registry -v ON_ERROR_STOP=1 -f 02_seed.sql
psql -U postgres -d tender_registry -f queries/01_top_companies_last_month.sql
psql -U postgres -d tender_registry -f queries/02_participation_funnel.sql
```

Проверено на PostgreSQL 16. Схема рассчитана на чистую базу и не содержит
`DROP`: запуск по ошибке на рабочей базе ничего не удаляет.

Файлы в UTF-8 и объявляют свою кодировку первой строкой: иначе psql берёт
кодировку клиента из локали системы, и на русской Windows файлы не
применяются.

## Модель данных

| Название | Таблица | Назначение |
|---|---|---|
| Компании | `companies` | Заказчики закупок и участники, подающие ставки |
| Тендеры | `tenders` | Отслеживаемые закупки |
| Лоты | `lots` | Части тендера, на которые подаются ставки |
| Ставки | `bids` | Предложения компаний по лотам |
| Исполнители | `performers` | Физлица, самозанятые и ИП |
| — | `lot_performers` | Назначение исполнителей на лоты |

Принятые решения:

- **Компании — одна таблица** и для заказчиков, и для участников. Одна
  организация объявляет закупки и участвует в чужих; роль определяется тем,
  куда подставлена ссылка: `tenders.customer_id` — заказчик,
  `bids.company_id` — участник.
- **Ставка ссылается на лот**, а не на тендер. Лоты одного тендера достаются
  разным компаниям, и без разбиения по лотам сумма выигранного неисчислима.
- **Победитель — признак на ставке** (`bids.is_winner`). Ссылка
  `lots.winner_bid_id` создала бы второй источник правды и циклическую
  зависимость таблиц.
- **Исполнители связаны с лотами «многие ко многим»**: на лот идёт несколько
  человек, один человек работает на нескольких лотах.
- **`companies.is_self`** отмечает свою компанию. Статус тендера означает
  исход её участия, а не состояние процедуры на площадке: у площадки закупка
  не бывает «проиграна».

Статусы тендера — тип `tender_status`: `draft` (Черновик), `active`
(Активен), `won` (Выигран), `lost` (Проигран).

## Ключи и ограничения

Внешние ключи:

| Ссылка | При удалении родителя |
|---|---|
| `tenders.customer_id` → `companies` | `RESTRICT` |
| `lots.tender_id` → `tenders` | `CASCADE` |
| `bids.lot_id` → `lots` | `CASCADE` |
| `bids.company_id` → `companies` | `RESTRICT` |
| `lot_performers.lot_id` → `lots` | `CASCADE` |
| `lot_performers.performer_id` → `performers` | `RESTRICT` |

Каскад — там, где дочерняя запись без родителя не имеет смысла. `RESTRICT` —
там, где удаление означало бы потерю истории: компанию со ставками и
исполнителя с назначениями удалить нельзя.

Ограничения:

- Три `CHECK` на тендерах связывают статус с датами: у черновика нет номера в
  реестре и дат процедуры; дата итогов заполнена тогда и только тогда, когда
  статус `won` или `lost`; даты идут по возрастанию.
- ИНН компании — 10 или 12 цифр, ИНН исполнителя — 12.
- Суммы ставок, начальные цены и номера лотов положительны.
- Уникальны: ИНН компании, ИНН исполнителя, номер в реестре, номер лота
  внутри тендера.
- Деньги — `numeric(15,2)`: двоичная плавающая точка даёт расхождение в
  копейках при суммировании. Метки времени — `timestamptz`: отбор за период
  не должен зависеть от часового пояса сессии.

## Индексы

| Индекс | Назначение |
|---|---|
| `bids_single_winner_per_lot_idx` | Уникальный частичный: не более одной победившей ставки на лот. Одновременно путь доступа к победителям в запросе 1 |
| `companies_single_self_idx` | Уникальный частичный: не более одной своей компании |
| `tenders_decided_at_idx` | Частичный, только завершённые закупки: отбор периода в запросе 1 |
| `tenders_active_bids_close_idx` | Частичный, только активные закупки: ближайшие закрытия приёма заявок |
| `tenders_customer_id_idx` | Закупки заказчика; внешний ключ |
| `bids_lot_id_idx` | Все ставки по лоту; внешний ключ и каскадное удаление |
| `bids_company_id_idx` | Ставки компании в запросе 2; внешний ключ |
| `lot_performers_performer_id_idx` | Лоты исполнителя: обратное направление составного первичного ключа |

Два правила целостности выражены уникальными частичными индексами, потому что
`CHECK` видит только одну строку. Индексы по внешним ключам созданы вручную:
PostgreSQL под них индексы не заводит, а без индекса на дочерней стороне
страдают и соединения, и проверка при удалении родителя.

Отдельного индекса по `lots.tender_id` нет — соединение по нему обслуживает
индекс уникальности `(tender_id, lot_number)`, где `tender_id` идёт первым.
Индексов по столбцам, не участвующим в запросах, нет: каждый индекс
замедляет вставку.

## Запрос 1: топ-3 компании по сумме побед за прошлый месяц

Возвращает место, компанию, ИНН, сумму побед, число выигранных лотов и
тендеров.

Допущения:

- период — прошлый календарный месяц, полуинтервал `[начало, конец)`;
- дата — подведение итогов, а не публикация: закупка, объявленная в мае и
  решённая в июле, относится к июлю;
- сумма — сумма победивших ставок, а не начальных цен лотов;
- единица учёта — лот.

Место считается `dense_rank()`. Мест ровно три, но строк может быть больше:
при равных суммах место делят несколько компаний. `LIMIT 3` отрезал бы одну
из равных произвольно, и результат менялся бы между запусками.

Результат на демонстрационных данных:

| Место | Компания | Сумма побед | Лотов | Тендеров |
|---|---|---|---|---|
| 1 | ООО «Дельта» | 5 000 000.00 | 2 | 2 |
| 2 | ООО «Меридиан» | 3 000 000.00 | 1 | 1 |
| 3 | ООО «Аргус» | 2 000 000.00 | 1 | 1 |
| 3 | ООО «Вектор» | 2 000 000.00 | 1 | 1 |

ИП Соколов с суммой 500 000 занимает четвёртое место и в выборку не попадает.

## Запрос 2: воронка участия своей компании по месяцам

Возвращает по месяцам подведения итогов: сколько лотов заявлено, сколько
выиграно, конверсию, её изменение к предыдущему месяцу в процентных пунктах,
сумму побед, среднюю скидку от начальной цены и число занятых исполнителей.

Допущения:

- участие — количество лотов, а не ставок: повторная ставка на тот же лот не
  является новым участием;
- идущие закупки не учитываются: их исход неизвестен;
- скидка считается только по победам.

Назначения исполнителей агрегируются отдельно и присоединяются по месяцу:
прямое соединение размножило бы строки ставок по числу исполнителей на лоте и
удвоило счётчик побед.

Сумма побед в месяце без побед — ноль, средняя скидка — пусто. Ноль означал бы
победы по начальной цене, которых не было.

Результат на демонстрационных данных, прогон 18.08.2026:

| Месяц | Лотов | Побед | Конверсия, % | Δ, п.п. | Сумма побед | Скидка, % | Исполнителей |
|---|---|---|---|---|---|---|---|
| 2026-06-01 | 2 | 1 | 50.0 | | 1 500 000.00 | 16.7 | 2 |
| 2026-07-01 | 5 | 1 | 20.0 | −30.0 | 2 000 000.00 | 20.0 | 2 |
| 2026-08-01 | 1 | 0 | 0.0 | −20.0 | 0 | | 0 |

Месяцы сдвигаются вместе с датой прогона.

## Демонстрационные данные

Семь компаний, десять тендеров, двенадцать лотов, двадцать пять ставок, три
исполнителя. Набор подобран так, чтобы на нём проявлялись ошибки запросов:

- две компании с одинаковой суммой побед делят третье место;
- лоты одного тендера выиграны разными компаниями;
- три ставки одной компании на один лот — в сумму должна попасть только
  победившая, иначе у «Вектора» выйдет 6 400 000 вместо 2 000 000;
- итоги одного тендера подведены за 10 минут до конца прошлого месяца,
  другого — через 10 минут после его начала.

Даты вычисляются от начала текущего месяца, а не заданы константами: запрос
за прошлый месяц возвращает непустой результат в любой день прогона.

## Границы решения

- Правило «ставка не выше начальной цены лота» в схеме не выражено: оно
  межтабличное, `CHECK` видит только свою строку. Потребовался бы триггер или
  дублирование цены в ставку.
- Контрольная сумма ИНН не проверяется, только формат.
- Согласованность статуса тендера с наличием победившей ставки своей компании
  — правило приложения, а не схемы.
- Миграций нет: схема применяется одним скриптом на чистую базу.
